NVC 패턴
- 화면을 담당하는 뷰 템플릿을 뷰라고 한다. 뷰는 컨트롤러와 모델이라는 두 동료가 있다.
- 컨트롤러는 클라이언트의 요청에 따라 서버에서 이를 처리하는 역할을 한다.
- 모델은 데이터를 관리하는 역할을 한다.
- 이렇게 웹 페이지를 화면에 보여주고(View), 클라이언트의 요청을 받아 처리하고(Controller),
  데이터를 관리하는(Model) 역할을 나누는 기법을 MVC 패턴이라고 한다.

정리
1. ( 뷰 템플릿 )이란 웹 페이지를 일종의 틀로 만든 것이다.
2. ( 컨트롤러 )는 클라이언트의 요청을 받아 서버에서 이를 처리하는 역할은 한다.
3. ( 모델 )은 뷰템플릿에서 사용되는 테이터를 관리하는 역할은 한다.
4. ( @Controller )는 이 클래스가 컨트롤러임을 선언한다.
5. ( @GetMapping )은 클라이언트의 URL 요청을 받아 특정 컨트롤러의 메서드가 처리하게 한다.

JPA는 왜 필요할까?
Client -> Server --[JPA]--> Database
- 자바 코드와 데이터베이스(SQL)은 사용하는 "언어"가 다르다.
- 자바는 객체 중심으로 사고하고, DB는 테이블(행/열)로 사고한다.
- 이 둘을 이어주는 다리 역할을 하는 것이 JPA이다.
- JPA 덕분에 우리는 SQL 문법을 직접 작성하지 않고도, 자바 객체의 메서드 호출만으로 DB에 데이터를
- 넣고 뺄 수 있다.
-> 이런 방식을 ORM(Object-Relational Mapping) 이라고 부른다.
-> JPA는 자바 진영의 ORM 표준 명세이기 때문이다.

Create 처리 흐름 전체 그림
1. Client(폼) -> Server(Java) --[JPA]--> Database(SQL)
    - 서버가 자바 객체를 그냥 DB로 던지면 DB는 "이걸 어떻게 저장하라는 거지?"하고 알아듣지 못한다.
    - 여기에 JPA가 통역사처럼 끼어들면 DB가 "ok"하고 알아듣게 된다.
2. Server -> [Entity, Repository]--JPA--> Database
    - Entity: DB 테이블과 1:1로 매핑되는 자바 클래스
    - Repository: Entity를 실제로 DB에 저장/조회/수정/삭제하는 창구(인터페이스)
3. Client(<form>) -> Controller(DTO) -> Entity로 변환 -> Repository.save() -> Database(Table)
    - DTO는 폼에서 막 받아온 날 것의 데이터 포장지
    - Entity는 DB 테이블 모양에 딱 맞게 다듬어진 데이터
    - Repository는 그 Entity를 실제로 테이블에 INSERT 해주는 "창구 직원"


롬복과 리팩토링 - 반복 코드 줄이고, println()을 로깅으로 바꾸기

1. 리팩터링의 정의를 설명할 수 있다.
2. 롬복이 왜 필요한지, 어떤 반복을 줄여주는지 이해한다.
3. build.gradle 에 롬복 의존성을 추가하고 IntelliJ 플러그인까지 설치한다.
4. @AllArgsConstructor, @ToString 으로 DTO/Entity의 반복 코드를 제거한다.
5. println() 이 실무에서 왜 문제가 되는지 설명하고, @Slf4j + log.info()로 대체한다.
6. 롬복 적용 직후 흔히 만나는 실행 오류와 대처법을 안다.

롬복이란?
- 코드를 간소화해주는 라이브러리이다.
- 개발하다 보면 getter(), setter(), constructor(), toString() 과 같은 필수 메서드들을 매번 작성하는데
  이를 매번 손으로 작성하는 것은 번거롭다.
  이런 반복 작업을 없애고 싶어서 나온 도구가 롬복이다.

로깅이란?
- 로깅 기능을 통해 println() 문을 개선할 수 있다.
- 로깅이란 프로그램의 수행 과정을 기록으로 남기는 것을 말하는데, 일종의 자동차 블랙박스와 같다고 생각하면 이해하기 쉽다.
- 평소엔 눈에 안 띄자만, 문제가 생겼을 때 "언제, 어디서, 무슨 일이 있었는지"를 되짚어볼 수 있게 해주는 장치이다.

리팩터링이란?
- 코드의 기능에는 변함 없이, 코드의 구조 또는 성능을 개선하는 작업을 말한다.

왜 println()을 쓰면 안될까?
- 현재 코드를 보면 println()문으로 확인하고 싶은 데이터를 출력하고 있다.
- 실제 서버에서는 절대 이렇게 하면 안된다!!
- println()문으로 데이터를 검증하면 기록에 남지 않을뿐더러, 서버의 성능에도 악영향을 끼친다.
  1) 성능 저하 및 병목 현상 유발: println() 같은 표준출력 I/O 작업을 수반하며, 이는 상대적으로 비용이 많이 드는 작업니다.
  2) 로그의 휘발성 및 추적 불가: 서버에서 println()으로 출력한 데이터는 일반적으로 표준 출력 스트림으로 나가며, 별도의 설정 없이는
     파일로 기록되지 않고 사라진다.

HTTP 메서드와 CRUD. SQL의 대응 관계
- HTTP의 대표적인 메서드로 GET, POST, PATCH, DELETE가 있다.
- POST : 데이터 생성 요청
- GET : 데이터 조회 요청
- PATCH, PUT : 데이터 수정 요청
- DELETE : 데이터 삭제 요청
-> 데이터의 생성, 조회, 수정, 삭제는 데이터 관리에서 가장 기본이 되는 동작이다.
   이를 간단히 CRUD라고 한다. 이러한 CRUD는 SQL문으로 적용할 수 있다.
         HTTP       - SQL
Create - POST       - insert
Read   - GET        - select
Update - PATCH(PUT) - update
Delete - DELETE     - delete

API
- Application Programming Interface
- 애플리케이션을 간편히 사용할 수  있게 하는, 미리 정해진 일종의 약속으로, 사용자와 프로그램 간 상호작용을 돕는다.
- 예를 들어 자판기를 생각해보면,
- 자판기 버튼이 하나의 API라고 볼 수 있다.
- 콜라 버튼을 누르면 콜라가, 사이다 버튼을 누르면 사이다가 나오는 것은 각 버튼에 따라 변환될 음료를 미리 약속했기 때문이다.
- 이와 마찬가지로 '윈도우 API'는 윈도우 개발을 위해 미리 정해진 약속, '자바 API'는 자바 개발을 위해 미리 만들어진 약속
- 이번에 우리가 다룰 REST API는 클라이언트와 서버 사이의 상호 작용, 즉 HTTP 요청에 따른 JSON 응답에 대한 약속이다.

XML과 JSON
- XML은 사용자 정의형 HTML 정도로 이해하면 된다.
- JSON은 자바 스크립트 방식을 차용한 객체 표현식 정도로 이해하면 된다.
- JSON 데이터는 키와 ㄱ밧으로 구성된 정렬되지 않은 속성의 집합이다.
- 키는 문자열이므로 항상 " "으로 감싸고, 값은 문자열인 경우에만 " "로 감싼다.

HTTP 상태 코드 정리
1xx(정보) - 요청이 수신되 처리 중이다.
2xx(성공) - 요청이 정상적으로 처리되었다.
3xx(리다이렉션 메시지) - 요청을 완료하려면 추가 행동이 필요하다.
4xx(클라이언트 요청 오류) - 클라이언트의 요청이 잘못돼 서버가 요청을 수행할 수 없다.
5xx(서버 응답 오류) - 서버 내부에 에러가 발생해 클라이언트 요청에 대해 적절히 수행하지 못했다.

HTTP와 RestController

1. @RestController가 일반 @Controller와 어떻게 다른지 설명할 수 있다.
2. REST API의 URL을 CRUD 기준으로 설명할 수 있다.
3. @RequestBody를 이용해 요청 본문(json)을 DTO로 받아올 수 있다.
4. ResponseEntity를 이용해 HTTP 상태 코드와 데이터를 함께 받아올 수 있다.
5. Get, Post, Patch, Delete 요청을 각각 처리하는 메서드를 작성할 수 있다.
6. 잘못된 요청에 대해 400(Bad Request) 응답을 만들 수 있다.

REST API를 구현하기 위해 REST API의 주소, 즉 URL을 먼저 설계해보자
GET -> /api/articles
GET -> /api/articles/{id}
POST -> /api/articles
PATCH -> /api/articles/{id}
delete -> /api/articles/{id}


서비스 계층과 트랜잭션

1. 컨트롤러와 리포지토리 사이에 서비스 계층을 두는 이유를 이해한다.
2. 관심사의 분리 원칙에 따라 기존 REST 컨트롤러를 리팩터링 하여 서비스 계층을 분리할 수 있다,
3. 트랜잭션과 롤백 개념을 이해한다.
4. @Service, @Transactional 어노테이션의 역할을 수행할 수 있다.
5. Java 스트림 문법을 활용해 리스트 데이터를 다룰 수 있다.

서비스란?
- 서비스란 컨트롤러와 리포지토리 사이에 위치하는 계층으로,
- 서버의 핵심 기능(비즈니스 로직)을 처리하는 순서를 총괄한다.

트랜잭션
- 일반적으로 서비스의 업무 처리는 트랜잭션 단위로 진행된다.
- 트랜잭션이란 모두 성공해야 하는 일련의 과정을 뜻한다.
- 트랜잭션이 실패로 돌아갈 경우 진행 초기 단계로 되돌리는 것을 롤백이라 한다.


테스트 작성하기

1. 테스트의 개녑과 필요성을 이해한다.
2. 테스트 케이스, 레팩터링, 디버깅, TDD(테스트 주도 개발)의 관계를 설명할 수 있다.
3. JUnit5를 이용해 서비스 계층의 동작을 겁증하는 테스트 코들르 작성할 수 이싸디
4. 테스트 코드 사이의 데이터 오염 문제를 이해하고, @Transactional로 이를 해결할 수 있다.

테스트란?
- 코드를 수정하다 보면 여기저기서 예상침 소한 문제들이 발생하낟. 코드의 양이 많아질수록 더 그렇다.
    하지만 코드 검증을 자동화하면 어떨까?
- 서비스 계층의 동작을 검증하기 위한 테스트 코드 작성법을 이해하고 연습해보자
-> 테스트란 프로그램의 품질을 검증하는 것으로, 의도대로 프로그램이 잘 작동하는지 확인하는 과정이다.

테스트 케이스
- 테스트 코드는 다양한 경우를 대비해 작성해야 핝다. 이를 테스트 케이스라고 한다.
- 테스트 케이스는 성공할 경우뿐 아니라, 실패할 경우도 고려해야 함.
- 예를 들어 하나의 기능에 대해서도 여러 케이스를 나눠서 작성한다.
    1) A_Success 성공 케이스
    2) A_Fail 실패 케이스
    3) B_Success_1, B_Success_2 성공 케이스 여러개
    2) B_Fail_1, B_Fail_2 실패 케이스 여러개

TDD(Test Drive Development, 테스트 주도 개발)
- 테스트를 통한 코드 검증과 리팩터링은 개발자의 기본 소양ㅇ;다.
- 이를 기반으로 한 개발의 방법론인 테스트 주도 개발 또한 개발의 핵심 패러다임으로 자리 잡고 있다.
- TDD란 일단 테스트 코드를 만든 후, 이를 통과하는 최소한의 코드부터 시작해 점진적으로 코드를 개선 및 확장해 나가는 개발 방식이다.


댓글 엔티티와 리파지터리

1. 게시글과 댓글의 관계를  일대다 / 다대일 개념으로 이해한다.
2. 기본기(PK)와 외래키(FK)의 역할과 관계를 이해한다.
3. @ManyToOne, @JoinColumn 어노테이션으로 Comment 엔티티를 설계하고 구현한다.
4. CrudRepository가 아닌 JpaRepository를 상속받아 CommentRepository를 구현한다.
5. @Query 어노테이션과 orm.xml 파일이라는 두 가지 방식으로 네이티브 쿼리 메서드 작성
6. @DateJpaTeset, @DisplayName()을 ㅣ용ㅇ해 리파지터리 테스트 코드를 작성

게시글과 댓글의 관계 - 일대다 / 다대일
- 하나의 게시글에는 여러 개으이 댓글이 달릴 수있다.
    -> 하나의 게시글에 많은 댓글이 달린다. 이런 관계를 일대다 관계
- 반대로 댓글으 ㅣ입장에서 보면, 여러 개의 댓글이 하나의 개시글에 속한다.
    -> 거꾸로 댓글 입장에서보면 여러 댓글이 하나의 게시글에 달리므로 many-to-one 다대일 관계라고 한다.
- 즉, 같은 관계ㅡㄹㄹ 어느 쪽에서 바라보느냐에 따라 일대다 / 다대일로 다르게 부른다.

기본기(PK)와 외래키(FK)
- article과 comment 테이블은 id를 기준으로 서로 관계를 맺고 있다.
    -> 두 테이블 모두 자신을 대표하는 id가 있는데, id와 같이 자신을 대표하는 속성을 기본키라고 한다.
        기본키는 동일테이블 내엣거 중복된 값이 없어야 하며ㅡ null 값을 가질 수 없다.
- comment 테이블에는 자신을 대표하는 id외에, 연관 대상을 가리키는 article_id 컬럼이 하나 더 있다.
    -> article_id와 같이 연관된 대상을 가리키는 속성을 외래키라고 한다.
       외래키를 따라가면 해당 댓글이 어떤 게시글에 달린 것인지 알 수 있다.
결론 : Comment 엔티티와 Article 엔티티는 다대일 관계로 설계하여, 댓글에서 게시글을 찾아갈 수 있도록 한다.
