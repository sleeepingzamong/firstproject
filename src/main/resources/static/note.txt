NVC 패턴
- 화면을 담당하는 뷰 템플릿을 뷰라고 한다. 뷰는 컨트롤러와 모델이라는 두 동료가 있다.
- 컨트롤러는 클라이언트의 요청에 따라 서버에서 이를 처리하는 역할을 한다.
- 모델은 데이터를 관리하는 역할을 한다.
- 이렇게 웹 페이지를 화면에 보여주고(View), 클라이언트의 요청을 받아 처리하고(Controller),
  데이터를 관리하는(Model) 역할을 나누는 기법을 MVC 패턴이라고 한다.

정리
1. ( 뷰 템플릿 )이란 웹 페이지를 일종의 틀로 만든 것이다.
2. ( 컨트롤러 )는 클라이언트의 요청을 받아 서버에서 이를 처리하는 역할은 한다.
3. ( 모델 )은 뷰템플릿에서 사용되는 테이터를 관리하는 역할은 한다.
4. ( @Controller )는 이 클래스가 컨트롤러임을 선언한다.
5. ( @GetMapping )은 클라이언트의 URL 요청을 받아 특정 컨트롤러의 메서드가 처리하게 한다.

JPA는 왜 필요할까?
Client -> Server --[JPA]--> Database
- 자바 코드와 데이터베이스(SQL)은 사용하는 "언어"가 다르다.
- 자바는 객체 중심으로 사고하고, DB는 테이블(행/열)로 사고한다.
- 이 둘을 이어주는 다리 역할을 하는 것이 JPA이다.
- JPA 덕분에 우리는 SQL 문법을 직접 작성하지 않고도, 자바 객체의 메서드 호출만으로 DB에 데이터를
- 넣고 뺄 수 있다.
-> 이런 방식을 ORM(Object-Relational Mapping) 이라고 부른다.
-> JPA는 자바 진영의 ORM 표준 명세이기 때문이다.

Create 처리 흐름 전체 그림
1. Client(폼) -> Server(Java) --[JPA]--> Database(SQL)
    - 서버가 자바 객체를 그냥 DB로 던지면 DB는 "이걸 어떻게 저장하라는 거지?"하고 알아듣지 못한다.
    - 여기에 JPA가 통역사처럼 끼어들면 DB가 "ok"하고 알아듣게 된다.
2. Server -> [Entity, Repository]--JPA--> Database
    - Entity: DB 테이블과 1:1로 매핑되는 자바 클래스
    - Repository: Entity를 실제로 DB에 저장/조회/수정/삭제하는 창구(인터페이스)
3. Client(<form>) -> Controller(DTO) -> Entity로 변환 -> Repository.save() -> Database(Table)
    - DTO는 폼에서 막 받아온 날 것의 데이터 포장지
    - Entity는 DB 테이블 모양에 딱 맞게 다듬어진 데이터
    - Repository는 그 Entity를 실제로 테이블에 INSERT 해주는 "창구 직원"


롬복과 리팩토링 - 반복 코드 줄이고, println()을 로깅으로 바꾸기

1. 리팩터링의 정의를 설명할 수 있다.
2. 롬복이 왜 필요한지, 어떤 반복을 줄여주는지 이해한다.
3. build.gradle 에 롬복 의존성을 추가하고 IntelliJ 플러그인까지 설치한다.
4. @AllArgsConstructor, @ToString 으로 DTO/Entity의 반복 코드를 제거한다.
5. println() 이 실무에서 왜 문제가 되는지 설명하고, @Slf4j + log.info()로 대체한다.
6. 롬복 적용 직후 흔히 만나는 실행 오류와 대처법을 안다.

롬복이란?
- 코드를 간소화해주는 라이브러리이다.
- 개발하다 보면 getter(), setter(), constructor(), toString() 과 같은 필수 메서드들을 매번 작성하는데
  이를 매번 손으로 작성하는 것은 번거롭다.
  이런 반복 작업을 없애고 싶어서 나온 도구가 롬복이다.

로깅이란?
- 로깅 기능을 통해 println() 문을 개선할 수 있다.
- 로깅이란 프로그램의 수행 과정을 기록으로 남기는 것을 말하는데, 일종의 자동차 블랙박스와 같다고 생각하면 이해하기 쉽다.
- 평소엔 눈에 안 띄자만, 문제가 생겼을 때 "언제, 어디서, 무슨 일이 있었는지"를 되짚어볼 수 있게 해주는 장치이다.

리팩터링이란?
- 코드의 기능에는 변함 없이, 코드의 구조 또는 성능을 개선하는 작업을 말한다.

왜 println()을 쓰면 안될까?
- 현재 코드를 보면 println()문으로 확인하고 싶은 데이터를 출력하고 있다.
- 실제 서버에서는 절대 이렇게 하면 안된다!!
- println()문으로 데이터를 검증하면 기록에 남지 않을뿐더러, 서버의 성능에도 악영향을 끼친다.
  1) 성능 저하 및 병목 현상 유발: println() 같은 표준출력 I/O 작업을 수반하며, 이는 상대적으로 비용이 많이 드는 작업니다.
  2) 로그의 휘발성 및 추적 불가: 서버에서 println()으로 출력한 데이터는 일반적으로 표준 출력 스트림으로 나가며, 별도의 설정 없이는
     파일로 기록되지 않고 사라진다.

HTTP 메서드와 CRUD. SQL의 대응 관계
- HTTP의 대표적인 메서드로 GET, POST, PATCH, DELETE가 있다.
- POST : 데이터 생성 요청
- GET : 데이터 조회 요청
- PATCH, PUT : 데이터 수정 요청
- DELETE : 데이터 삭제 요청
-> 데이터의 생성, 조회, 수정, 삭제는 데이터 관리에서 가장 기본이 되는 동작이다.
   이를 간단히 CRUD라고 한다. 이러한 CRUD는 SQL문으로 적용할 수 있다.
         HTTP       - SQL
Create - POST       - insert
Read   - GET        - select
Update - PATCH(PUT) - update
Delete - DELETE     - delete

API
- Application Programming Interface
- 애플리케이션을 간편히 사용할 수  있게 하는, 미리 정해진 일종의 약속으로, 사용자와 프로그램 간 상호작용을 돕는다.
- 예를 들어 자판기를 생각해보면,
- 자판기 버튼이 하나의 API라고 볼 수 있다.
- 콜라 버튼을 누르면 콜라가, 사이다 버튼을 누르면 사이다가 나오는 것은 각 버튼에 따라 변환될 음료를 미리 약속했기 때문이다.
- 이와 마찬가지로 '윈도우 API'는 윈도우 개발을 위해 미리 정해진 약속, '자바 API'는 자바 개발을 위해 미리 만들어진 약속
- 이번에 우리가 다룰 REST API는 클라이언트와 서버 사이의 상호 작용, 즉 HTTP 요청에 따른 JSON 응답에 대한 약속이다.

XML과 JSON
- XML은 사용자 정의형 HTML 정도로 이해하면 된다.
- JSON은 자바 스크립트 방식을 차용한 객체 표현식 정도로 이해하면 된다.
- JSON 데이터는 키와 ㄱ밧으로 구성된 정렬되지 않은 속성의 집합이다.
- 키는 문자열이므로 항상 " "으로 감싸고, 값은 문자열인 경우에만 " "로 감싼다.
